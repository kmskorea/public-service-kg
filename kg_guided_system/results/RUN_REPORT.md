## 요약

- **실행은 끝까지 됐다.** pytest 80/80, curl 확인 2/2, 예시 질문·이해도 평가 2회·시스템 비교(15문항 × 3시스템)를 모두 마쳤다.
- **원래 계획과 다른 점이 두 가지 있다.**
  1. GPU 0의 빈 메모리가 다른 사용자 작업 때문에 부족해서, BF16이 아니라 **같은 모델 파일을 vLLM이 불러올 때 FP8로 양자화**해서 돌렸다.

- **이해도 평가**: 수치·지역 90%, 범주 재현율 70%. 놓친 범주 7개가 전부 **추출(①) 단계 문제**다. LLM 연결(②)은 재현율을 올리지 못했고(LLM 사용 70% = 미사용 70%), 정밀도만 80% 대 75%로 조금 높다. 연결 단계의 실제 문제는 이 채점에 잡히지 않는다. LLM이 설계에서 정한 연결 방향(상위 개념만 고른다)을 자주 어기는데, 정답 라벨이 하나라도 섞여 있으면 맞은 것으로 채점되기 때문이다(3장 참고).
- **시스템 비교**: 질문당 적합 건수 평균이 KG 60.5 / KG-base 246.9 / RAG 3.5건이다. 질문당 LLM 호출은 3.7 / 3.6 / 5.0회, 평균 시간은 26 / 32 / 85초다. 근거 검사 경고는 KG 1, KG-base 0, RAG 3건이다.

## 3. 실행 결과

### 3-0. 고친 코드 (실행을 막는 오류)

**`judge/extract.py` `vocabulary()`**: 추출 프롬프트에 넣는 '대상 범주 어휘 120개'의 순서가 실행할 때마다 달랐다.
- **원인**: `concept_usage()`가 서비스 조건 set을 순회하며 횟수를 세므로, 횟수가 같은 범주끼리의 순서가 파이썬 문자열 해시 시드에 따라 바뀐다.
- **영향**: 요청 본문이 달라지면 캐시 키도 달라진다. 그래서 `LLM_CACHE_MODE=only`로 재생하면 추출 단계에서 매번 CacheMiss가 난다(발표 시연을 GPU 없이 재생할 수 없음). 결과 자체도 실행마다 달라졌다. 첫 실행에서는 u10이 '자립준비청년'을 추출했는데, 다른 프롬프트 순서에서는 놓쳤다.
- **수정**: `most_common()`을 `sorted(items, key=(-횟수, IRI))`로 바꿔, 횟수가 같으면 IRI 순으로 고정했다(2줄).
- **판정 규칙·테스트는 바꾸지 않았다.** 다시 돌린 pytest도 80 passed다.
- **확인**: 가짜 LLM으로 KG·KG-base·RAG 전체 요청을 해시 시드 1·2·3에서 비교했다(`logs/determinism_probe.py`). 고치기 전에는 추출 요청만 달랐고, 개념 확인·RAG 판정·답변 요청과 순위는 같았다. 고친 뒤에는 모두 같았다.
- 첫 실행(고치기 전, 비교 단계에서 중단)의 캐시와 결과는 버리고 3단계를 빈 캐시로 다시 돌렸다. 아래 수치는 모두 다시 돌린 결과다.

**재생 확인**: 다른 해시 시드(12345)와 `LLM_CACHE_MODE=only`로 ask, eval_understanding, compare_systems를 다시 실행했다.
- 캐시 미스 0건.
- `ask` 출력, `compare.md`(시간 값 제외), `pool_for_annotation.csv`가 원래 실행과 같았다.
- 캐시 파일은 바뀌지 않았다.

**알아 둘 점 (GPU 비결정성)**: 같은 요청을 temperature 0으로 다시 보내도 답변 문장이 조금 달라졌다(예: '확인해 주세요' ↔ '확인 부탁드립니다'). 판정과 순위는 같았다. 캐시가 같은 요청에 같은 응답을 돌려주므로 시연 재생에는 영향이 없다.

  - ¬기초생활수급자 → ¬기초연금 수급자
  - ¬주택소유자 → ¬농지소유자, ¬산림소유자, ¬토지 소유자
- 정답이 아닌 것을 같은 대상으로 보았다.
  - 주택소유자 → 주택 거주자, 토지 소유자

## 4. 문제가 보이는 실제 답변 (5개)

1. **u03 KG: 말하지 않은 사실과 엉뚱한 상위 순위.** "1958년생 … 기초연금 받고 있어요 … 난방비 지원"에 대해:
   - 답변이 "「서울특별시 수도요금 감면」: **기초생활수급자이시므로** …"라고 썼다. 사용자는 기초연금만 말했고, 추출이 기초생활수급자를 지어냈다.
   - 적합 상위 5건에 「귀화허가, 국적회복허가 신청 수수료 면제 안내」, 「특별공로자 및 우수인재 특별귀화 허가 신청 수수료 면제 안내」, 「불법사금융예방대출」이 있다.
   - 확인 필요로 「한부모가족 지원」을 권했다.
   - 정작 난방비 사업은 KG 답변에 없다. RAG는 「에너지복지요금 지원」을 찾았다.
2. **u05 KG: 유일한 적합이 무관한 사업.** "임신 7개월 … 서대문구":
   - 받을 수 있는 사업이 「농식품 수출 해외정보 제공」("대한민국 국민이시므로") 하나뿐이다.
   - 확인 필요 상위에 「고효율 냉동기 지원」, 「민간건축물 대상 지진안전 시설물 인증제 …」가 있다.
   - KG-base와 RAG는 「임신축하금 지원」, 「서울시 임산부 교통비 지원」 등을 냈다. 추출에서 키워드가 비어(관련 사업 없음) 일반 범주로만 맞는 사업이 위로 왔다.
   - 근거 검사 경고 1건(사업명 축약)도 이 답변이다.
3. **u13 KG: 어색한 되묻기와 태그 노출.** "… 지금 일자리 구하는 중이에요"에 "혹시 '구직자/실업자'에 해당하시나요? **[되물 질문]**"이라고 물었다.
   - 이미 말한 것을 되묻는다(추출 누락 때문).
   - 프롬프트의 `[되물을 질문]` 표시가 답변에 그대로 나왔다. 이렇게 태그가 나온 답변은 45개 중 9개다(KG 3, KG-base 5, RAG 1).
   - KG-base는 u08 카페 주인에게 '중소기업', u12 농업인에게 '기관/단체'에 해당하는지 물었다.
4. **u04 KG: 같은 사업을 두 범주에 넣었다.** 1순위 적합이 취업 준비 중인 북한이탈주민에게 「고속도로 졸음쉼터 푸드트럭 창업 지원」이다. 같은 사업이 답변의 '받을 수 있는 사업'과 '확인이 필요한 사업'에 둘 다 나온다. 첫 문장 "취업 준비 중이신 점 안타까워하며"도 상담 어조로 어색하다.
5. **u01 RAG: 지역을 명백히 오판정했다.** 신당동(중구) 주민에게 영등포구 사업인 「기초수급자 명절 위문금 지급」을 확인 필요로 넣고, 마지막에 "**신당동이 영등포구에 속하는지** 확인해 주실 수 있나요?"라고 물었다. RAG는 다른 질문에서도 지역·자격과 무관한 것을 적합으로 냈다.
   - u04: 「EM(유용 미생물)발효액 무상 배부」
   - u03: 「다문화 이해 교육 제공」
   - u03: 한센병사업대상자인지 되물음

참고로 KG-base는 적합이 평균 247건으로 지나치게 많다(조건이 덜 걸려 있기 때문). u01 대학생에게 「가정폭력 피해자 보호시설 퇴소자 자립지원금」이 적합 상위 2위로 나왔다.

## 5. 고치면 좋을 것 (우선순위 순, **제안만 했고 고치지 않았다**)

1. **개념 확인 프롬프트·코드에서 연결 방향을 강제한다** (`judge/linker.py`). 긍정 표현에는 '그 개념 또는 더 넓은 개념'만 고르게 하고, 한정어(지역명·저소득·청년·위기·여성·채무조정 등)가 붙은 후보는 고르지 말라는 예시를 넣는다. LLM이 고른 것 가운데 KG `broader*` 관계가 반대 방향인 것은 코드에서 버리는 것도 방법이다. 잘못된 '적합'과 '✓ 필수' 충족(u01 의료급여 수급자, u08 강서구 소상공인)을 바로 줄인다.
2. **제외 조건이 걸린 사업을 '받을 수 있어요'로 쓰지 않게 한다.**
   - 답변 프롬프트(`judge/answer.py` SYSTEM): '다음에 해당하면 제외'가 있고 사용자 범주와 관련이 있어 보이면 '확인 필요'로 옮기거나 제외 조건을 반드시 쓰게 한다.
   - KG 쪽: '생계·의료·주거·교육급여 수급자'와 '기초생활수급자'를 잇는 관계를 넣는다(팀 KG 작업, u01 「희망두배 청년통장」).
3. **추출 프롬프트에 암시된 범주 예시를 넣는다** (`judge/extract.py` GUIDE).
   - 추가할 예시: 취업 준비·일자리 구함 → 구직자, 혼자 산다 → 1인가구, 보육원·시설 퇴소 → 자립준비청년, 결혼 n년 → 신혼부부, 임신 → 여성, 회사원 → 근로자, 귀농 → 귀농인.
   - 금지할 것: "가족(딸·아버지)의 범주는 본인 groups에 넣지 않는다", "기초연금 ≠ 기초생활수급자, 들은 말만 쓴다".
   - 코드 쪽: birth_year가 있으면 나이를 코드가 계산해 age보다 우선한다(u03).
   - 이해도 평가에서 놓친 7건이 모두 여기서 나왔다.
4. **'일반 범주만 맞는' 사업을 위로 올리지 않는다.** 대한민국 국민·일반인·지역주민만으로 충족된 사업을 '그 밖에 적합' 순위와 답변 근거(S8~S10)에서 뒤로 보낸다(푸드트럭, 귀화 수수료, 농식품 수출정보). 판정 규칙(`judge.py`)은 그대로 두고 `pipeline.py`의 순위나 `answer.py`의 근거 선택에서 처리할 수 있다.
5. **답변 프롬프트를 정리한다.**
   - `[되물을 질문]` 표시를 쓰지 말고 질문 문장만 쓰게 한다(9/45 노출).
   - '신청 기간 아님'이면 그렇다고 쓰게 한다(u01).
   - 같은 사업을 두 범주에 넣지 않게 한다(u04).
   - 공감 표현은 쓰지 않게 한다.
6. **되물을 질문을 고른다.** 개인 사용자에게 '법인/시설/단체', '기관/단체', '중소기업'을 묻지 않는다. 사용자가 이미 말한 것(추출 누락)을 되묻는 문제는 3번으로 줄어든다.
7. **이해도 평가 채점에 '방향 오류' 지표를 추가한다.** 정답 라벨이 섞여 있으면 맞은 것으로 보는 지금 방식으로는 1번 문제가 보이지 않는다. 연결된 개념 중 정답보다 좁은 개념의 비율을 따로 센다.
8. **7인 이상 기준중위소득을 공식 값으로 바꾼다** (아래 6장).
9. **발표 수치를 BF16으로 다시 돌릴지 정한다.** GPU에 64GiB 이상 자리가 생기면 같은 명령으로 BF16을 돌리고 FP8 결과와 비교한다. 캐시 키에 양자화 정보가 없으므로 다른 캐시 파일(`LLM_CACHE=…`)을 써야 한다.

RAG(B1)는 비교 대상(baseline)이라 지역 필터를 넣지 않았다. 넣으면 비교 조건이 바뀌므로 넣을지는 팀이 정할 일이다.
